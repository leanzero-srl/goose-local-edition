# Forge two-build desktop sequence

One Run action in the desktop Benchmark view creates a durable Forge series with two different native child run IDs. Electron main owns the sequence: leaving the view does not stop it, and renderer events cannot start build two. Each child uses the existing single native run_build.py launcher, a fresh work directory, the normal 300-call allowance and its own canonical verdict. Three scoring fixture sites belong to one independent model build.

Both children use one private captured provider configuration and environment. The unchanged native exporter rereads the frozen private profile before launch, and its snapshot must match the original binding. Host Settings edits cannot change the pending child. Task, kit, scorer, engine and literal request fields are rechecked before each child. The private provider snapshot contains credentials, stays outside public records, uses restricted permissions, and is removed after the sequence ends. The desktop retains its existing Forge medium-effort selection; this change does not claim the campaign controller's separate provider eligibility qualification policy.

Main writes child completion and series state atomically. Build two starts after build one's scored result and comparison identity are saved. The parent remains reserved between children. Cancel preserves completed evidence and skips queued work. On restart, saved canonical results are recovered before an unfinished sequence is marked interrupted; reading history never replays paid work. Deleted or rescored evidence is reread before admitting the aggregate.

The local summary reports two comparable completed builds, their median and observed range. One completed build is provisional. Mismatched or missing comparison evidence preserves individual scores and explains why a comparable pair is unavailable. An observed range is not a population confidence interval.

Pair publication uses the existing per-build native publisher and its media, body and identity guards. Each child is posted once. Accepted first-child history survives a second-child refusal. A synchronous renderer reservation and a main-process owner prevent rapid repeated clicks or competing windows from entering simultaneous publication. The canonical pair is reread before either child is submitted.

An inert native exporter control exercises host Settings A→B→A using non-account credentials and no model call. The isolated development desktop uses a separate profile and the existing engine.

Offline desktop history controls import the two original Opus raw verdicts as an explicitly artificial test grouping. They verify real main-process canonical readback and real UI rendering; they are not new model work and do not prove a paid app-owned pair has completed. The native two-build paid journey must be exercised after a compatible release is installed safely outside the frozen active campaign. Existing campaign runs continue through the installed native Benchmark view; this prospective source change does not rewrite them.
