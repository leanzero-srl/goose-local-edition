## Authorization and ambiguity attack

Preflighting the saved confirmed key through repeatable confirm before Up is acceptable. It is an authenticated idempotent confirmation write, not a read-only endpoint; no review request executed it. The actor path checks account status, exact account/device, current revision/expiry and revocation; desktop-controller enrollment remains denied. The response must still match native deviceID/controller role/unrevoked state. Fresh owner authorization and TLS pinning remain mandatory after mesh recovery; mesh confirmation does not grant content scopes.

Only exact remote403/code mesh_binding_unverified may create a replacement intent. This error alone does NOT prove absence: wrong key/account/preauth binding, expired/tagged node or changed enrollment authority can also produce it. The subsequent existing join call is the deciding authority. It reads a complete provider snapshot, validates isolation/account mapping, rejects unknown/unactivated nodes and outstanding untracked keys, and refuses replacing a previous confirmed binding when the same nodeID remains usable. usable ignores online, so merely offline is not permission to replace. Changed identity on a still-usable node is therefore denied, not repaired locally. Existing policy also treats expired/tagged nodes as unusable; describe the contract as absent/unusable, not strictly absent.

Provider HTTP401/403/404/5xx becomes502provider_failed; network failures, malformed bodies, incomplete pagination, ambiguous identities and account mismatches remain provider errors. Generic native401/403, enrollment_mismatch, mesh_binding_changed, scope/revocation errors,409already_enrolled/update_required and provider failures must neither mint with a fresh ID nor delete local mesh state. A revoked controller credential fails before provider mint and is rechecked during reservation/finalization; this path cannot restore a revoked device.

## Required persistence correction

The proposal must make these transitions explicit in code/tests. Persist pendingReplacementID before its first join request and reuse it after cancellation, lost response or secure-write failure. A retry with pending intent should call join for that same ID directly rather than generating another ID or depending on the old confirmation path again. The server may already have revoked the old enrollment and reserved/issued the replacement even when the client never received its response.

Retain old local enrollment state until join returns a validated credential for the exact pendingID. Complete old-node shutdown, then recheck lifecycle/cancellation before any reset. Either delete the old directory before committing the new enrollment record, or persist a resetNeeded state that MUST be completed before Up on every restart. Never write replacement.join with confirmedNodeKey=nil while leaving an old directory with no durable reset marker: a crash would restart the old identity with replacement metadata. If deletion or final secure write fails, preserve resumable same-ID intent and do not start a node with mixed state. A returned-but-not-persisted join can be fetched again using the savedID; do not trade away old state on an ambiguous response.

409enrollment_pending means an external mint outcome is unresolved, not a retry with a new UUID.409expired/denied/provider failure must remain explicit under the current proposed scope; no automatic remint loop. Preserve authority device credentials, account identity and unrelated controller caches; no owner mutation replay.
