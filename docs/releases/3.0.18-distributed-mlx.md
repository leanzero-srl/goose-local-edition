# 3.0.18 Distributed MLX engine, and cut-off replies are errors

One model can now be split across several Macs over Thunderbolt, supervised by goose and kept apart from the single-Mac engine (only one of them owns this Mac at a time; starting distributed while a model is mounted is refused by name). Before anything loads, a preflight checks every node — reachability, available memory against the planned slice with headroom, the model on every node, the Thunderbolt link and, for JACCL, the RDMA address table — and refuses with the numbers. Each rank runs under memory caps set as ratios of its node's RAM. The supervisor treats a stream that ends without [DONE] as a failure, declares a hang when progress stops for ten times the running median, stops the local half first and verifies the remote half is gone by pid, and restarts per policy. A memory watchdog closes admission at WARN and stops cleanly at CRITICAL instead of riding into a kernel panic.

Measured live with the owner's Qwen3.8-27B over JACCL between an M4 Max and an M3 Ultra: a 62-minute soak 275/275 OK; a frozen rank mid-stream detected by the progress rule (median 2,183 ms, bound 21,830 ms, silent 22,323 ms) and restarted; a killed rank surfaced in 2 s; WARN closed admission with a 503 and a reason while the running stream finished; CRITICAL stopped both halves.

The Engine tab, the tile and the tray show the mode ("Single · this Mac" / "Distributed · 2 nodes · JACCL"), a Distributed engine section carries preflight, start/stop, per-node memory and the supervisor's events.

Across every provider, a reply stream that ends without its protocol's completion marker (finish_reason or [DONE]; message_stop; response.completed/incomplete; finishReason; messageStop) is now a named error instead of a shorter answer presented as complete.
