# 3.0.94 Gauntlet scores a sync that never reached its recovery faults

**A build whose sync never reaches the scheduled faults now scores zero on those checks instead of being refused.**

- **What happened:** Gauntlet 7.2 tests recovery by injecting two faults into the vendor during the app's first sync: a dropped connection and a 500 with Retry-After. Each fires at a scheduled page. GLM-5.3's app started its first sync partway through the list with a cursor the vendor had never issued, and reached the end after 58 requests. Neither fault page was ever served, so the two recovery checks had nothing to measure, and the scorer refused the whole build.
- **The fix:** when the vendor's trace proves the app's first sync made fewer requests than a fault needs, that recovery check scores zero. Its detail states the counts taken from the trace: the requests made and the requests the fault needed.
- **Still refused:** a missing vendor trace, a missing fault schedule, or a first sync that made enough requests but never saw the fault still refuse, because those point at the test harness rather than the app.
- **Nothing else changes:** the benchmark task, the vendor and every other check are the same. Gauntlet 7.1 keeps its frozen behaviour.
