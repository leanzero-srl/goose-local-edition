# 3.0.122 — token usage on every published run, Forge 2.0 pairs published together, the run-audit backlog

## Token usage

Every benchmark publish now carries the run's token usage (`tokenUsage`): prompt, completion, cached and reasoning
tokens, the number of model calls, and a split per model (the entrant and goose's helper calls).

- An OpenRouter run reads OpenRouter's own record for every generation id the run kept, again at publish time. Records
  that were not ready when the run ended (the harness bill then said "incomplete") are usually there by then. The read
  has one 75-second budget; past it, the publish falls back to the run's own bill.
- The records are checked against goose's own per-call counts for the same calls. If the two disagree in either
  direction, the counts go out as a lower bound with a note naming the gap, never as exact.
- When the run-end bill was incomplete only because records were missing, and the re-read now finds all of them, the
  bill is completed from those records and says how many were missing at the end of the run. A bill incomplete for any
  other reason is left as it was.
- A local run uses the engine's own counts; a direct provider with no per-call records (Google) uses goose's per-call
  usage. The source is always named.
- leanzero.net validates the field, shows it on the run page and in the board preview ("exact", "at least …" for a lower
  bound, "about …" for an estimate), keeps the stronger count when a run is re-scored, and labels counts on community
  entries as reported by the publisher. An older site that does not know the field gets the run without it.

The 179 runs already on the board were backfilled from OpenRouter's records where they exist (124 exact), from goose's
counters or the local engine otherwise, and estimated for 6 Bedrock runs.

## Forge 2.0 pairs

A Forge 2.0 run is two builds. Publishing either build of a finished series now publishes both in one action: both are
checked first (same model, provider, task and operator decision), then posted in build order, so they land as one entry
with two builds. A series with one scored build publishes that build alone, a partner that cannot be published does not
block the other, and a partial failure can be retried for the missing build only. If the two builds cannot be one
entry, the card offers to publish them separately; the app never couples mismatched builds.

## Run-audit backlog

- I-33: a remote provider stream that goes silent after the answer has started is ended as a retryable error after
  `GOOSE_STREAM_STALL_SECONDS` (default 600, 0 = off) and re-sent. Any data line counts as progress, including tool-call
  arguments streaming slowly; keepalive comments do not. Local engines are never judged (by host name or by the
  connection's private peer address), because they can be legitimately silent during prefill.
- I-28: an engine loop stop (`rapid_mlx_stop_reason: repetition`) is treated as a loop, not as an output-length cut:
  goose keeps one copy of the repeated text, nudges "you kept repeating", and a loop stop inside a tool call fails that
  call with the loop named instead of running it with cut arguments.
- I-9: goose reads the context window an engine names in a context refusal, sizes compaction to it for the rest of the
  session, and cuts the transcript middle to fit instead of ending. A memory-cap refusal is never read as a window.
- I-3: the model planner counts stacked mixture-of-experts layers (`switch_mlp`), so models like Xing and LFM2 plan.
- Engine Rapid-MLX v0.14.3-lz.13: the repetition guard also stops exact repeats of 129-1024 tokens (tool-bearing
  requests only, `--repetition-guard-max-period`), the loop stop reason is on the wire, models whose template speaks
  the `<tool_call>`/`<function=` wire get the qwen3_coder_xml parser automatically (Nex-N2.5-mini), and a prompt that
  already closed the think block starts its answer as content.

I-25 (the stop reason recorded for a run refused on a provider error) stays open: it lives in the pinned Forge 2.0
benchmark files, and changing them would change the task.
