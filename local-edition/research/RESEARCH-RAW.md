A deterministic compiler/import check is a ground-truth oracle the 27B model does not have to be smart enough to run itself; and threading the real traceback into the retry turns a blind re-roll into a targeted fix, which weak models benefit from far more than strong ones.

### [STRONG] Deterministic project-level integration gate: pytest --collect-only + entry-point smoke run after the build  (effort M, risk med, vet_conf 0.7)
- IDEA: This is the strongest deterministic answer to three of the four A/B failures (contract drift, built-but-unwired entry points, no end-to-end run). After scheduler.run returns and before the run is declared successful (swarm.rs tail, the report block ~3990+), run two deterministic ground-truth checks as subprocesses in the working dir: (1) `python3 -m pytest --collect-only -q` — this IMPORTS every test module and its targets across the whole project without running tests, so a cross-module ImportError / missing-symbol drift surfaces loudly even when each module's tests passed in isolation; (2) if the layout is a CLI (an all_files entry contains `__main__.py` or `cli.py`), derive the package name and execute `python3 -m <pkg> --help` and assert exit code 0 — a broken argparse, bad import, or crashing main() that every unit test missed fails here deterministically. On failure, don't silently report success: either fail the run with the captured traceback in the report, or (preferred) fire ONE corrective re-dispatch of an `integrate-verify`-style fix task whose description IS the real traceback. This converts the prompt-only 'you MUST actually run the program end-to-end' instruction (swarm.rs ~3196-3204, 2393-2405) — which a weak model routinely skips while claiming PASS — into a gate the harness runs itself. --help is always side-effect-safe; keep the richer spec-derived smoke command as the existing prompt-only step since synthesizing real CLI args deterministically is not reliable.
- WHY LOCAL: The whole point of integrate-verify is defeated by a weak model that reports 'PASS' without ever invoking pytest or the binary — verbal self-report is the least trustworthy signal from a 27B model. collect-only and an exit-code-checked `--help` are ground truth that needs zero model intelligence, and they target precisely the unwired-entry-point and isolation-test-blindness failures the A/B exposed on multi-module apps (the cohesive-app case already passes, so the gate mostly fires exactly where qwopus only drew).
- WHERE: crates/goose-cli/src/commands/swarm.rs run_swarm, after `scheduler.run(...)` and before the core_failed success determination (the report/`core_failed` block near the file tail, ~3985-4097); reuse the existing ProcCommand subprocess pattern already used for `lms ps`/`curl` (swarm.rs 922-947) and the integrate-verify dispatch path for the corrective re-dispatch.
- FLAG: GOOSE_SWARM_SMOKE (env, default off). Gate also self-disables when the working dir has no Python entry point / no tests, so text-only tasks, non-Python projects, and cloud/upstream runs are untouched.
- VET: feasible=True helps_local=True :: FEASIBLE. The insertion point is real: after `scheduler.run(...)` returns (swarm.rs ~4002) and before the `core_failed` success determination (~4086-4095). The ProcCommand subprocess pattern (922-947) is exactly reusable, and the harness process cwd is the project root where workers write files (std::env::current_dir is used throughout, e.g. 3186), so subprocesses run in the right place. The simple variant (fail the run / append traceback to the report) is unambiguously implementable. 

HELPS WEAK LOCAL: yes, and it is NOT cloud cargo-culting. The codebase ALREADY concedes the exact failure this targets — the prompts at 2386-2405 and 3196-3204 verbally beg the model to 'actually RUN the program end-to-end' and warn that a green suite hides broken argparse/imports/unwired entry points. A 27B routinely claims PASS without doing it; converting that prompt-only plea into a harness-run gate is the right move and matches the author's stated A/B failures. `pytest --collect-only` genuinely catches cross-module ImportError/contract-drift that per-module isolated runs miss — legitimate ground truth needing zero model intelligence.

RISKS / VERIFY FIRST (why med, not low):
1. Exit-code discrimination is load-bearing and under-specified. `pytest --collect-only` returns 5 when NO tests are collected and 2 on collection (import) errors; 127/nonzero if pytest isn't installed. The 'self-disables when no tests' claim MUST be implemented by treating exit 5 (and pytest-missing) as skip/pass and ONLY exit 2 as failure — not by file presence. Get this wrong and you get false failures on a weak fleet. Workers are only ever TOLD to run `python3 -m pytest`; pytest availability in the harness's python3 is assumed, not verified — confirm it.
2. Package-name derivation for `python3 -m <pkg> --help` has real edge cases: src-layout (`src/pkg/__main__.py` needs cwd=src or PYTHONPATH), nested packages, and flat `cli.py` at root (where `--help` may not even be wired). These produce FALSE --help failures. Also note `--help` short-circuits argparse and never runs main()'s body, so it catches import/argparse-construction errors only — narrower than 'end-to-end run'. The author scopes this honestly (keeps real-arg smoke prompt-only), so it's fine, but don't oversell --help.
3. The 'preferred' auto re-dispatch is more plumbing than 'reuse the path' implies: `dispatcher` is MOVED into `scheduler.run` at ~3999 and `devices` is moved into `Scheduler::new` at 3971, so you must clone the `Arc<dyn TaskDispatcher>` and stash a device_id/model_id BEFORE those moves, then hand-build a DispatchRequest (dispatch.rs:38) and call `.run()` directly. Doable. But given the fork's documented worker-loop tendency, a FALSE-positive gate auto-firing a corrective re-dispatch risks a wasteful loop on the weak fleet — ship the simpler 'fail + traceback in report' variant first, prove the gate's signal is clean on a live run, then add re-dispatch. Env-gate GOOSE_SWARM_SMOKE default-off keeps blast radius contained, which is correct.
