# goose model-benchmark — design

_Frozen 2026-07-28. Researched from published methodologies (Artificial Analysis, HELM, Terminal-Bench, tau-bench, LMArena, MLPerf, Aider, SWE-bench Verified, LocalScore) and grounded in goose's actual event stream. Sources in the findings section._

## What this is

goose runs a frozen suite on the user's OWN local fleet and scores it. What is scored is the user's **model x quantization x hardware x goose build x lever profile** — not goose. Four axes: inference, generation, correctness, delivery.

## Headline verdict

A single headline NUMBER is not defensible and we will not ship one. The measured replicate spread (8/15, 13/15, crash on byte-identical config/binary/spec) means a scalar score from any run count we can realistically ask a user to sit through is a point estimate whose own noise is larger than most differences people would want to read off it. Publishing "qwen3.6-27b: 412" would be noise dressed as a measurement, and the first user who runs it twice and gets two different numbers turns the reputational goal negative.

What replaces it: a headline BAND plus a stability figure, never separable. The headline slot renders `GB 412 [354-468] · n=15 · pass^5 1/3` — a geometric mean of the four axis scores with a bootstrap 95% interval (resample the n runs with replacement 1000x, recompute all four axes and the composite each time, take the 2.5/97.5 percentiles), the sample size, and the tau-bench-style consistency figure (how many of the 3 specs passed on EVERY replicate). Rules that make it honest: (a) the composite is only emitted at n>=15 — smoke (n=1) and light (n=3) render axis cards and the replicate strip with the composite slot reading "not scoreable — n too low", and the desktop Benchmark button defaults to medium (3 specs x 5 reps = 15); (b) the interval is never suppressed, never collapsed to the midpoint, and never shown without n; (c) two results whose bands overlap are rendered TIED, and the UI refuses to rank them; (d) beside the band we print the minimum detectable effect from the run's own replicate variance — "at n=15 this can only separate models that differ by more than ~X points" — which pre-empts the "I ran it twice" complaint by stating the instrument's resolution before anyone finds it.

The honest shape of this product is NOT a leaderboard. It is a per-machine diagnostic with error bars, whose four axis cards and replicate strip ARE the product, and whose composite is a convenience for people who want one line. Two structural things follow. First, the composite must be a GEOMETRIC mean, so a model that decodes fast but never ships a working app cannot land mid-table — a zero on any axis correctly zeroes the composite. Second, the thing being scored is honestly (model x goose build x lever set x fleet size x hardware), not the model alone. "goose is just a collection of prompts and code, the models get pointed out" is the framing that will be attacked first and it is measurably wrong for agent harnesses — the same model scores differently under different harnesses. So every result is labelled `qwen3.6-27b Q5_K_M x goose 1.41.94 (4382dd350) x 3 nodes`, with build_sha and scoring_version next to the headline, and cross-build comparison is refused in the UI rather than merely discouraged.

One verified constraint that changes the design: in the archived runs I inspected, `run_started.gates` was `{complete:false, goals:false, contracts:false, review:false, smoke:false, ...}` — all off — so `complete_result`, `smoke` and `review` never appear in those streams. The delivery axis's headline sub-metric (false-green rate) depends on `complete_result`. Benchmark mode must therefore PIN the gate set as part of the frozen profile; it cannot read whatever the user happens to have on.

## Scoring model

### CORRECTNESS — did the thing it built actually work (highest weight because it is the only axis graded by RUNNING the artifact)

**Weight:** 35% of the composite

**Sub-metrics:**

- pass@1: mean over the n runs of (deterministic checks passed / checks total). The frozen suite is 14 checks over 3 specs — crud: imports/help/golden-value/golden-json/tests; compute: imports/help/golden-precedence/golden-rightassoc/tests; txn: imports/help/golden-nested-rollback/tests (sub-weight 0.45)
- pass^k: fraction of the 3 specs where EVERY one of the k replicates passed EVERY check. This is the metric that carries the 8/15 -> 13/15 -> crash story instead of averaging it away (sub-weight 0.30)
- functional verdict: fraction of built trees where harness/functional.py assess() returns 'functional' — it runs every advertised command bare AND with a bad argument, or binds the server and GETs / (sub-weight 0.25)

**Normalization:** All three are already fractions in [0,1]; identity map to 0-100, no anchors needed and none invented. 'unprobeable' counts in the DENOMINATOR and never the numerator, exactly as functional.py:234 summarise() already does ('an app we could not probe is not an app we showed to work'). Interval: Wilson score 95%, then CLUSTERED by SPEC — the design is 3 clusters x k replicates, and naive SEs on this shape can be >3x too small. With only 3 clusters the intervals will be embarrassingly wide; that is shown, not softened.

**Source:** evals/swarm-gym/harness/bench.py SUITE[*].checks (type=command_succeeds, run with no API key and no LLM judge) + harness/functional.py assess()/summarise(). EXPLICITLY EXCLUDED as sources: complete_result.passed, task_completed.status, judge_verdict.verdict, and any model self-report — functional.py's own docstring records the measured false-green cases (h1-treat-2 reported passed+verified on an app whose every command crashed; verify-6 passed+verified while raising an uncaught sqlite3.DatabaseError). NO NEW INSTRUMENTATION NEEDED.

### DELIVERY — did the run finish, was it honest about finishing, and did it use the fleet

**Weight:** 25% of the composite

**Sub-metrics:**

- COMPLETION (binomial): a run counts only if run_finished was emitted AND complete_result is present. A crash emits no run_finished — that absence IS the crash detector. Crashed and timed-out runs score 0 and are NEVER dropped from the denominator (sub-weight 0.30)
- HONESTY = 1 - false_green_rate, where false_green_rate = fraction of runs emitting complete_result{passed:true} whose functional.py verdict is 'broken' or whose golden checks failed. This is the headline sub-score and the most novel number goose can publish (sub-weight 0.35)
- FLEET EFFICIENCY: time-based occupancy from harness/occupancy.py — sum(task_completed.elapsed_ms) / (execute wall-clock x |run_started.pool|), wall window from first task_dispatched to last task_completed (sub-weight 0.20)
- TIME TO DELIVER: median run_finished.phases.total_min (verified shape: {research_min, planning_min, execute_min, gates_min, total_min}) (sub-weight 0.15)
- PENALTIES subtracted from the axis, capped at -20 pts total: counts of task_retry with transient=false, low_confidence_ask_timeout, complete_stall_exit, complete_missing_deliverables, cross_module_drift

**Normalization:** Completion and honesty are fractions -> identity. Occupancy: log-ratio against FROZEN anchors floor 5% / ceil 60%, chosen from the 31-run archive measurement (median 22.1%, mean 24.4%, max 47.2%) so today's fleet lands mid-scale and a ceiling exists. Time: inverted log-ratio, floor 180 min / ceil 15 min. Anchors are constants compiled into the binary and tagged scoring_version='gb-1'; changing one REQUIRES a version bump and old results keep their old tag. Never min-max across submissions — a user's score must not move because a stranger submitted a faster Mac.

**Source:** run_finished (verified: {event, report{done,failed,bonus,results,dispatched_per_device,tasks,per_device}, phases, ts, run_id, seq}), complete_result, task_completed{task_id,status,device,model,attempts,elapsed_ms,session_id,ts,seq}, task_dispatched{task_id,device,model,attempt,deps,owned_files,context_slice_len}, task_retry{task_id,from_device,error,transient}, run_started.pool (verified: array of {id,model_id,weight,instances}), cross_module_drift, complete_stall_exit, complete_missing_deliverables, low_confidence_ask_timeout, plus harness/functional.py for the honesty cross-check. NEW INSTRUMENTATION: none in the engine, BUT benchmark mode must PIN run_started.gates — in every archived run I inspected gates were ALL FALSE, so complete_result/smoke/review were absent and the honesty sub-score would be unbuildable. Use run_finished.phases.dispatch_occupancy_* only as a labelled contrast, never as the scored figure: dispatch-count occupancy rates one 78-minute serial task the same as ten 2-minute parallel ones.

### INFERENCE — what the local fleet can actually do, measured directly rather than inferred

**Weight:** 25% of the composite

**Sub-metrics:**

- DECODE: median stats.tokens_per_second over 3 repeats at the 1024-prompt / 512-generate config
- PREFILL: median stats.time_to_first_token at the 16384-prompt config, inverted — this is what a long-context swarm actually pays
- CONTEXT HOLD: tokens_per_second(16384-prompt) / tokens_per_second(128-prompt) — the degradation ratio, where quantization and KV-cache choices actually show up
- DIAGNOSTIC ONLY, never scored: draft acceptance = accepted_draft_tokens_count / total_draft_tokens_count
- DIAGNOSTIC ONLY, never scored: 'effective in-run throughput' = sum(sessions.accumulated_output_tokens) / sum(task_completed.elapsed_ms), labelled explicitly as including tool and file-IO time so nobody reads it as a decode rate

**Normalization:** Log-ratio against frozen anchors: decode floor 5 tok/s, ceil 100 tok/s; TTFT floor 20 s, ceil 0.5 s (inverted); context-hold floor 0.25, ceil 1.0. pts = 100 * clamp(ln(x/floor)/ln(ceil/floor), 0, 1). The three scored sub-metrics carry EQUAL weight and combine by GEOMETRIC mean, so a catastrophic prefill cannot hide behind a good decode rate. Report median with a P5-P95 band and NO outlier trimming.

**Source:** NEW INSTRUMENTATION — REQUIRED, AND IT IS THE ONLY AXIS THAT NEEDS IT. The swarm event stream carries NO token counts; the only timing signals are task_completed.elapsed_ms, per_device busy_ms and run_finished.phases. So this axis is built from a dedicated pre-run probe against every node in run_started.pool over LM Studio's native endpoint: POST /api/v0/chat/completions -> stats{tokens_per_second, time_to_first_token, generation_time, stop_reason} and usage{prompt_tokens, completion_tokens, completion_tokens_details.reasoning_tokens, total/accepted/rejected_draft_tokens_count}; GET /api/v0/models -> quantization/arch/max_context_length/state for the run manifest. I re-verified GET /api/v0/models live on this machine today: three loaded nodes, Q5_K_M, arch qwen35, max_context_length 262144. The 'effective throughput' diagnostic joins task_completed.session_id to ~/.local/share/goose/sessions/sessions.db (accumulated_output_tokens), which harness/collector.py already opens read-only. HARD TRAP baked into the probe: max_tokens must never be below ~256 — a short-budget probe is dominated by ramp-up and reports the hardware ~5x slower than it is. HARD PRECONDITION: the fleet must be verified IDLE before probing or this measures contention, not capability.

### GENERATION — did the planning and the written work survive, rather than how much of it there was (SHIPPED AS v0.9, LOWEST CONFIDENCE, LOWEST WEIGHT)

**Weight:** 15% of the composite — deliberately the smallest, because it is the axis I trust least

**Sub-metrics:**

- PLAN ADEQUACY: plan_loaded.task_count inside a frozen per-spec band, plus plan_confidence, plus DAG invariants from harness/plan_shape.py (verified plan_loaded shape: {task_count, tasks[{id,deps,files,difficulty,model}]}) (sub-weight 0.30)
- REWORK: 1 - (non-transient task_retry + complete_fix_wave rounds) / plan_loaded.task_count (sub-weight 0.30)
- SELF-CONSISTENCY: 1 - normalized(cross_module_drift count + review.new_findings count + share of pre_review events with had_findings=true). Reads new_findings ONLY, never pre_existing_skipped (sub-weight 0.25)
- YIELD: bytes of code in the final tree reachable from the entry point / sum(sessions.accumulated_output_tokens) for that run's task sessions, with the engine's own orphan_files event as the direct counter-signal (sub-weight 0.15, HARD-GATED to zero unless that run's correctness > 0)

**Normalization:** All four are fractions or bounded ratios -> identity to 0-100, combined by weighted ARITHMETIC mean (not geometric — a single zero here is a plan-shape quirk, not a product failure). Rework and self-consistency are clamped at 0 from below.

**Source:** plan_loaded, task_retry{transient}, complete_fix_wave, cross_module_drift, review.new_findings, pre_review{task_id,device,had_findings}, orphan_files, harness/plan_shape.py, harness/collector.py _snapshot_files (already sha256'd), sessions.db accumulated_output_tokens. FLAGGED HONESTLY: this is the axis with no clean published precedent and the softest Goodhart surface — every intuitive proxy for 'generation' (lines, files, tokens) rewards exactly the wrong behaviour, and even 'yield' can be farmed by writing less, which is why the correctness gate is not optional. Expect to revise it after the first ~46-run dataset. The other three I would ship as designed.

## UI shape

THE BUTTON AND THE PREFLIGHT. A Benchmark entry in the desktop nav, gated on `const { isLocal } = useEdition()` so it never appears in an upstream-flavoured build. Landing view: a tier selector (custom DropdownMenu, never a native select) showing smoke / light / medium / high with the honest cost and the honest consequence next to each — "medium: 15 runs, ~4h, the only tier that produces a score"; smoke and light are labelled "diagnostic, not scoreable". Below it a live fleet preflight card: each node from GET /api/v0/models with its id, quantization, arch, max_context_length and loaded state, plus an IDLE check. The Run button is disabled while any node is busy, with the reason stated — a probe against a busy fleet measures contention, not capability.

THE RUN. One screen, three stacked bands. (1) The inference probe, running first while the fleet is quiet: 4 configs x 3 repeats x |pool|, with each node's decode and TTFT filling in live. (2) The replicate strip — the centrepiece — one solid-filled cell per run, laid out as 3 spec rows x k replicate columns, filling left to right in the interleaved order bench.py already uses (spec0, spec1, spec2, spec0, ...) so a partial run stays balanced. Each cell is a strong saturated colour: green all-checks-pass, amber partial, red broken, dark red crash (no run_finished), grey pending. This strip is the single most important thing on the screen, because it is where the user SEES that byte-identical inputs produce different outcomes instead of being told. (3) The current run's live phase timeline from the engine JSONL. A visible per-run cap and an abort that keeps partial results (interleaving means a partial run is still balanced across specs).

THE HEADLINE. A large solid number with its bracket, never separated: `412 [354-468]`, and directly under it, same visual weight, three facts — `n=15 · medium tier · pass^5 1/3`. Below that one plain sentence: "At n=15 this can separate results that differ by more than 38 points. Anything closer is noise." Under the number the identity line, not in small print: `qwen3.6-27b-coder Q5_K_M (qwen35, 262144 ctx) x goose 1.41.94 (4382dd350) x 3 nodes x scoring gb-1`. At smoke/light the number slot renders "not scoreable — n too low" in the same size, with the axis cards still populated. Comparing two saved results renders both bands on one scale; if they overlap the UI prints TIED and refuses to order them.

THE EXPANDED VIEW. Four axis cards, ordered by how much they can be trusted rather than by weight: correctness, delivery, inference, generation. Each card: the big solid score, the interval as a solid filled bar (no faded tint, no left accent rail), a one-line trust note ("graded by running the app, no LLM judge, no API key" / "self-reported hardware — the least verifiable axis"), then each sub-metric as a row of RAW VALUE -> POINTS -> SOURCE naming the literal event or grader:
  golden checks 41/70 -> 59 pts (bench.py SUITE command_succeeds)
  functional verdict 9/13 probed -> 69 pts (functional.py assess)
  decode 42.3 tok/s -> 71 pts (LM Studio stats.tokens_per_second, 1024x512, median of 9)
  prefill TTFT 6.8 s @16k -> 44 pts (stats.time_to_first_token)
  fleet busy 22% -> 31 pts (occupancy.py, sum task_completed.elapsed_ms / execute wall x |pool|)
  rework 3 retries / 8 tasks -> 62 pts (task_retry transient=false, plan_loaded.task_count)
Then three panels. RELIABILITY: pass@1 and pass^k side by side with the plain-English gloss — "right 62% of the time, but right on EVERY replicate for only 1 of the 3 specs." HONESTY: two bars, "runs that claimed success" vs "runs verified working", with the delta called out as the false-green rate and the two archived cases named as why the metric exists. WHAT THIS CANNOT TELL YOU: n, tier, the minimum detectable effect, the fact that the suite is 3 frozen CLI-app specs so this measures CLI-app construction and nothing else, and the plain statement that the score belongs to the model AND this goose build AND this fleet, not the model alone.

RUN MANIFEST, at the bottom, expandable and copyable: build_sha + version + crate_version from levers_resolved, the profile hash over the frozen suite + pinned levers + pinned gates, model id/arch/quantization/max_context_length per node, |pool| and node ids from run_started.pool, tier, scoring_version, and the sha256 of every run's JSONL. That block is what makes a submission auditable and what a skeptic re-derives the score from.

Design law applied throughout: solid saturated colours and bold numbers (the replicate strip is a full green/amber/red/dark-red set, not tints); no left accent rails anywhere; no faded 8-12% washes; no window.alert/confirm and no native select; only `--color-*` tokens from styles/main.css, since an undefined var() silently invalidates the whole declaration.

## Publish path (goose -> leanzero.net)

WEBSITE CHANGES THAT MUST LAND BEFORE ANY GOOSE CODE POSTS ANYTHING. All in ~/Projects/LeanZero-website, and that repo's CLAUDE.md mandates the "reiterate understanding and wait for confirmation" protocol before any work there — open with that step.

1. STOP PUBLISHING LIVE. src/app/api/benchmark-submissions/route.ts currently calls client.create(doc) with no drafts prefix, so an anonymous POST is publicly rendered within the 300s revalidate and the response literally says "Benchmark published". Change to an explicit draft id (`drafts.ab-${crypto.randomUUID()}`). This was proven fail-closed on this exact dataset with a positive control: authenticated, `count(*[_id in path("drafts.**")])` = 4; unauthenticated the same query = 0 — so drafts genuinely exist and are genuinely invisible, not merely absent. This also just restores the convention the repo already uses for blogSubmission and tutorialSubmission; benchmark is the only endpoint writing straight to a public rendered type. No read-path change needed.

2. KILL THE SSRF — this is more urgent than the publish-live issue and is live today regardless of the benchmark work. resolveImages() (route.ts:44-69) takes every image URL out of an unauthenticated request body and does a server-side fetch() with no scheme/host/IP validation, no size cap, no timeout, no redirect limit, inside Promise.all over an unbounded array. Delete the call from the public route. Since the document is now a draft awaiting review, editors add images in Studio anyway, so the feature costs nothing to remove — and allowlisting SSRF correctly (DNS rebinding, redirect chains, IPv6-mapped v4) is a larger change than deleting it.

3. FIX THE FORM REGRESSION IN THE SAME COMMIT. SubmitBenchmarkForm.tsx reads data.data?.slug and renders a "View it" link to /agentic-benchmarks/${slug}. Once submissions are drafts that URL 404s. Drop the slug from the 201 body, change the message to {success:true, status:"pending_review"}, and replace "Thanks — your benchmark is live." with a pending-review screen. Keep the field names, the exact 400 message strings the form surfaces verbatim, and the honeypot's silent 200-with-no-write byte-identical.

4. NEW STRUCTURED MACHINE ENDPOINT, SEPARATE FROM THE HUMAN FORM. POST /api/benchmark-runs writing a new `benchmarkRun` document type, markdown DISABLED entirely (plain-text notes only, strict allowlist parse rejecting unknown top-level keys, 256 KB body cap read via request.text() before JSON.parse). An endpoint that never accepts markdown cannot reach the image-fetch path at all. The four axes are numbers you need to sort and aggregate; stored as Portable Text prose they are useless for the reputational point. Always writes drafts too.

5. DURABLE RATE LIMIT WITHOUT NEW INFRASTRUCTURE. The current in-memory Map (5/10min) resets on every Lambda cold start and is not shared across instances — its own comment concedes it. Keep it as a first line, add a durable second check via Sanity itself: `count(*[_type=="benchmarkRun" && submitterHash==$h && _createdAt > $since])`, the same pattern src/app/api/mcp-keys/generate/route.ts already uses. Store HMAC-SHA256(ip, RATE_LIMIT_SALT), NEVER a raw IP — I verified the production dataset is publicly readable (unauthenticated GROQ returned 200 and 126 documents), so a raw IP written there is a new privacy leak, not a control. Do NOT extend the middleware matcher to cover /api: its first action is a trailing-slash redirect and many HTTP clients drop the body on redirect, which would break exactly the desktop POSTs being added.

6. SEPARATE AND URGENT, NOT PART OF THIS FEATURE: three apiKey documents in that public dataset currently expose real customer email addresses and MCP tenantIds to anonymous callers. Triage independently. It also constrains this design — never put a raw email or IP into that dataset.

AUTHENTICATION — THE USER, NEVER THE BINARY. State it plainly to the team: any API key, HMAC signing key or OAuth client secret compiled into a distributed desktop build is public. Electron ASAR archives are not encrypted (npx asar extract is the whole attack), strings finds constants in the Rust binary, and a user can simply proxy their own traffic. Obfuscation changes the time cost, not the outcome. Instead: goose opens https://leanzero.net/agentic-benchmarks/connect, the user enters an email, the site emails a one-time link via Resend (already wired — RESEND_API_KEY/EMAIL_FROM, with src/lib/resend/mcpKeyEmail.ts as the existing template pattern), clicking it mints a per-user submit token shown once, the user pastes it into goose, goose stores it in the OS KEYCHAIN and not in config.yaml. Every submission sends Authorization: Bearer. The site stores only sha256(token) plus a hashed email. If identity matters for credibility later, upgrade to OAuth 2.0 Device Authorization Grant (RFC 8628) against GitHub as a PUBLIC client with no client secret — the flow designed precisely for devices that cannot keep secrets — because "submitted by a verified GitHub account" is worth far more than an anonymous row.

WHAT GOOSE UPLOADS. Not a score. The bundle is the RAW EVIDENCE: every replicate's .swarm/run-<id>.jsonl verbatim including crashed and aborted runs, the levers_resolved object, build_sha + version + crate_version, the pinned benchmark profile hash (SHA-256 over canonicalised {suite prompt bytes, check definitions, full lever set, pinned gate set, tier, per-run cap}), the inference probe's raw stats/usage per node, per-check stdout and exit codes, functional.py verdicts, occupancy.py series, and the sha256 of each built app tree. Headers: Authorization: Bearer, Idempotency-Key: sha256 of the bundle. The server RECOMPUTES all four axes and the composite from the logs and ignores any score in the body — a score field is a claim, an event stream is a claim a forger has to keep internally consistent. Server responds 202 {status:"pending_review", id, publicUrl:null} — never "published".

SERVER-SIDE VALIDATORS (published as open source so the rules are inspectable): event ordering (run_started before task_dispatched before task_completed before run_finished), task_dispatched/task_completed reconciliation, sum(elapsed_ms) consistent with run_finished.phases and wall clock, spec prompt hashes matching the frozen suite, replicate count matching the declared tier, profile hash matching a published release, build_sha != "dev" (a plain cargo build reports "dev", which is a free exclusion), n >= 15 rejected below that with a 400 that explains why, and physically implausible throughput flagged.

THE BOARD ITSELF, THREE TIERS. SELF-REPORTED (default): a visually distinct, separately-sorted table with a literal count in the header — "N results, 0 verified, N self-reported" — and one sentence saying the submitter controlled the machine, the model, the client and the payload, and nothing here is checked. Never merged into a headline ranking, never used for a superlative. REPRODUCIBLE (machine-checkable, no human): all validators pass, released build_sha, n>=15, full bundle retrievable at a stable URL. VERIFIED: someone other than the submitter re-ran the same profile on the same model and hardware class and landed inside the published interval — either LeanZero's own reference fleet or an independent replicate. Only the VERIFIED tier gets the headline board, and it ships EMPTY rather than shipping an unlabelled mixed table. Add a public flag thread per entry; flagged entries drop out of the default view. Run the 3-node fleet on a fixed cadence and publish those runs with full logs as the calibration anchor, expressing community results as ratios to their hardware-class reference — and bank the reference's own replicate spread as the published noise floor, so any delta smaller than it renders "indistinguishable" rather than as a rank.

## Build order

1. 1. harness/score.py — the whole scoring model, OFFLINE, over data that already exists. Reads benchmark-runs.csv plus the archived .swarm/run-*.jsonl streams and emits the four axes, the composite, the bootstrap interval, the clustered Wilson intervals and the minimum detectable effect. No engine change, no UI, no network. This is the smallest defensible thing because it answers the only question that matters first — do the numbers exist and are they stable enough to publish? — and it can be checked against 31 archived runs today. If an axis cannot be computed from real archived data here, it does not ship.

2. 2. `goose benchmark` as a CLOSED-DIVISION subcommand. Forces the frozen bench.py suite and refuses any other spec source; PINS every lever AND the gate set (verified necessary: gates were all false in the archived runs, so complete_result never appeared and the honesty sub-score would have been unbuildable); aborts rather than warns if any env var, config file or flag deviates; emits a new benchmark_profile event carrying the profile hash; enforces replicates >= 5; writes one bundle directory. Verify by asserting the profile hash is identical across two runs and that complete_result now appears.

3. 3. The inference probe module + fleet-idle preflight. LM Studio /api/v0 against every node in run_started.pool, 4 frozen configs x 3 repeats, temperature 0, minimum 256 generated tokens, refusing to run if any node is busy. This is the only NEW instrumentation in the whole design, and it is additive — it runs before the swarm and writes its own file. Verify against the live fleet, whose endpoint I confirmed working today.

4. 4. The desktop Benchmark view, read-only and local. New route + nav item behind isLocal, an Electron IPC handler that reads the bundle from disk (main-process file read, no ACP method and no schema regeneration needed — the data is on the user's disk), the tier selector, the fleet preflight card, the live replicate strip, the headline band, the four axis cards and the expanded view. Verify over CDP on the installed app: assert the DOM rendered AND the engine JSONL says it happened, plus a screenshot, because two shipped changes in this repo were dead on arrival and only a live check found them.

5. 5. WEBSITE HARDENING — lands independently, no goose dependency, and should not wait for the desktop view. Draft-only writes, delete resolveImages(), fix the SubmitBenchmarkForm slug 404 in the same commit, body cap, HMAC'd durable rate limit. Separately triage the three apiKey documents leaking customer emails. After this, the worst case for the existing human form degrades from 'spam is live on leanzero.net' to 'a human deletes a row in Studio'.

6. 6. The machine path: benchmarkRun schema, POST /api/benchmark-runs with markdown disabled, the open-source validator set, server-side score recomputation, n<15 rejection, and the device-pairing flow (connect page + Resend one-time link + per-user token, stored in the OS keychain on the goose side). No shared secret in the binary at any point.

7. 7. Submit-from-desktop, plus the public board with the three tiers and the honest header count. Ship the VERIFIED tier empty. Start the reference-fleet cadence in the same increment, because a board without a calibration anchor is an uncalibrated absolute, and a stale anchor is worse than none.

8. 8. Held-out rotating spec, scored and displayed separately from the frozen suite, with divergence surfaced as a contamination warning rather than averaged in. Do this once the board exists, because it is the answer to the first credible accusation — 'the models were tuned to those three prompts'.

9. 9. Revisit the generation axis against the accumulated dataset (~46 runs) and either re-weight it, replace the yield sub-metric, or drop it to diagnostic-only. Bump scoring_version if anything moves; old results keep their old tag.

## Refusals — what this benchmark will NOT claim

- We will NOT publish a single scalar score. Every score is a band with n attached, and the composite is withheld entirely below n=15. Two results whose bands overlap are shown TIED and the UI refuses to order them.
- We will NOT claim to benchmark the MODEL. Every result is labelled model x quantization x goose build_sha x lever/gate profile x fleet size. The same model scores differently under a different harness, and cross-build comparison is refused in the UI rather than merely discouraged.
- We will NOT read any self-reported success as evidence. complete_result.passed, task_completed.status, judge_verdict.verdict and model prose never contribute to correctness — the measured false-green rate makes them worse than no signal. They are used only as the CLAIM side of the honesty metric.
- We will NOT drop crashes, timeouts or outliers. A crashed replicate scores 0 and stays in the denominator; dropping it is dropping the finding. No trimming on the timing measures either.
- We will NOT verify which model actually served the requests. goose talks to an OpenAI-compatible endpoint; a submitter can point it at a frontier cloud model and label it qwen3.6-27b, and `lms ps` output is client-reported text. There is no fix short of TEE attestation, which needs confidential-compute datacenter GPUs and does not exist on a Mac Studio or a consumer card. Stated on the page, not buried.
- We will NOT claim the binary is verified. build_sha comes from option_env! at compile time — it is a string the builder chooses, not a measurement. Requiring a released sha raises the effort bar and gives a free 'dev' exclusion; it proves nothing about the bytes that executed.
- We will NOT sign results client-side and will not pretend to. The key would ship to the adversary inside an unencrypted ASAR or a strings-readable binary, and even validate-then-run is beaten by a TOCTOU in the gap between check and execution. No shared secret in a distributed build, ever — authentication is per-user and revocable or it does not exist.
- We will NOT verify the submitter's hardware. Self-reported strings; a commercial team has fought fake entries in this exact category for fifteen years and still shows impossible results.
- We will NOT prove the artifact was built during the run. A pre-seeded repo, a warm cache or a locally swapped prompt all defeat a frozen suite, because the submitter can patch the thing doing the freezing.
- We will NOT publish one global cross-hardware ranking. A 27b on three consumer nodes and a 70b on a datacenter card are not the same measurement — per-hardware-class tables and points-per-VRAM / points-per-watt views instead.
- We will NOT present unverified rows as authoritative. Self-reported entries carry a literal count in the table header and never enter a headline ranking or a superlative. The verified tier ships empty rather than being faked full.
- We will NOT let a submitter silently retract. Selective disclosure — test many variants privately, publish the best — needs no forgery at all and is the mechanism that actually distorted a major leaderboard. Withdrawals are displayed.
- We will NOT claim the benchmark measures general model capability. It measures construction of small CLI applications under this swarm, on three frozen specs, and says so in the expanded view.
- We will NOT lower sampling temperature to make the variance look smaller. That moves conditional variance into the variance of conditional means and fakes precision we do not have.

## Open questions

- Does pinning the gate set (complete/review/smoke on) change the swarm's measured behaviour enough that benchmark numbers stop predicting normal-use behaviour? Every archived run I inspected had all gates false, so we have essentially no gates-on baseline — the first thing score.py should measure is the gates-on vs gates-off delta on the same spec, before the profile is frozen.
- How much wall time does a medium tier actually cost end to end (15 runs + probe), and is that a thing a user will sit through? bench.py caps a run at 3600s, so the worst case is ~15h. If the honest answer is 'nobody will run medium', the design needs either a resumable/background run or a lower scoreable floor — and lowering the floor means accepting wider bands, not pretending they are narrower.
- Adding SPECS buys more clusters and therefore tighter clustered intervals; adding REPLICATES does not. With only 3 specs the clustered SEs will dominate. Is expanding the frozen suite to 5-6 specs the right move before publishing anything — accepting that it breaks pairing with every existing archived result?
- Can benchmark-mode workers actually be network-isolated on macOS without breaking MCP/tool use? If not, the correctness axis includes an unknown amount of retrieval rather than generation, and the manifest must declare network:permitted and the board must treat those as a separate non-comparable class.
- Can the swarm write or edit the pytest files that grade it? If a worker can touch the test suite the correctness axis partly measures test-writing. This needs an audit of which files the graders read versus which files tasks own, plus a detector that flags any run whose event stream shows a worker touching the suite or the checks.
- Are the proposed frozen anchors (decode 5-100 tok/s, TTFT 20-0.5s, occupancy 5-60%, total_min 180-15) right, or will today's fleet pin against a ceiling or a floor? They must be set once from real data and then never moved without a scoring_version bump, so getting them wrong is expensive. score.py over the 31 archived runs should set them.
- Does the generation axis survive contact with real data at all, or should v1 ship with three axes and 40/30/30 weights? I would rather drop it than publish a farmable number — the decision should be made from the first 46-run dataset, not from taste.
- Is x-forwarded-for normalised by Amplify/CloudFront on this deployment? If not, the IP-hash rate limit is a deterrent only and the per-user token is doing all the work.
- How does Sanity Studio surface drafts.* documents with no published counterpart in this Studio version? The moderation workflow depends on a reviewer actually seeing them; needs a manual check before rollout.
- Who commits to running the reference fleet on a cadence, and what happens to published ratios when it goes stale? A stale anchor silently miscalibrates every community result derived from it, which is worse than having none.

### Leaderboard integrity for a self-reported, locally-run goose swarm benchmark published to leanzero.net — what existing leaderboards do about self-reporting, and what goose can/cannot verify

- THERE ARE ONLY THREE VERIFICATION REGIMES IN THE WILD, and every credible leaderboard picks one. (1) The operator runs the eval itself. (2) Peer review + audit among a closed set of named, accountable submitters. (3) Open self-report into a public database with no verification. goose is structurally in bucket 3 and cannot reach bucket 1 — the entire point is the user's own hardware and model. So the job is to build bucket 3 properly with a bucket-2 ladder bolted on top.
- REGIME 1 — Hugging Face Open LLM Leaderboard exists *because* self-reported numbers were worthless. HF's RLHF team could not reproduce published results: scores in papers and marketing releases were given without reproducible code and in most cases used prompt/eval setups optimized per model. Their fix was to run every model themselves, same questions, same order, same hardware. https://huggingface.co/blog/open-llm-leaderboard-mmlu and https://huggingface.co/docs/leaderboards/en/open_llm_leaderboard/about
- REGIME 1 also ships a community FLAG mechanism, which is the cheap half goose CAN copy: anyone can open a discussion reporting a suspicious model; confirmed cases get renamed with 'Flagged' and drop out of the default view. Contamination detection without pre-training data access is conceded to be very hard. https://huggingface.co/spaces/open-llm-leaderboard/open_llm_leaderboard/discussions/472
- REGIME 2 — MLPerf is a VENDOR SELF-SUBMISSION model that works only because of enforced structure: source code sufficient to replicate (preprocessing, weights, weight transformations, data traversal order, hyperparameters, RNG seeds), a <system_desc_id>.json hardware/software manifest, load-generator logs (mlperf_log_summary/detail/accuracy), compliance tests TEST01/04/06, a mandatory peer review ('each submitter is required to review at least one other submission'), a public objection process with 'fix_required' tags, and random audit of up to two Closed-division Available submissions per round, completed within 90 days. Code and logs must be made available to other submitters for auditing during the review period. https://github.com/mlcommons/policies/blob/master/submission_rules.adoc
- MLPerf's CLOSED vs OPEN division is the single most transferable idea: Closed = reference model used exactly as specified, all scenarios mandatory, apples-to-apples; Open = modifications allowed, no accuracy constraints, no compliance runs. The availability tiers (Available / Preview / RDI) additionally gate whether a result is even comparable. https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc
- MLPerf takes RUN-TO-RUN VARIANCE as a first-class design constraint, not a footnote: training requires 5 runs for vision (so 90% of entries from the same system fall within 5%) and 10 runs for everything else (within 10%), then DROPS the fastest and slowest and reports the arithmetic mean of the rest. Run counts were set by empirically studying reference-implementation behaviour. https://arxiv.org/pdf/1910.01500
- REGIME 2-lite — SWE-bench's 'verified checkmark': the submitter opens an issue in SWE-bench/experiments with instructions to run their system, and the SWE-bench team re-runs it on a RANDOM SUBSET. Submissions must include predictions plus reasoning traces/trajectories. Network access is disallowed during evaluation specifically to prevent cheating. https://github.com/SWE-bench/experiments and https://www.swebench.com/verified.html
- SWE-bench's actual cheating detection is a similarity script (detect_similarity.py) that strips comments, ignores files the gold patch didn't touch, parses to unidiff PatchSet, and looks for gold hunks appearing VERBATIM in the prediction. Baseline exact-match rates: 6.7% avg on Verified (0-13%), 4% on Lite, 2.45% on full. The one outlier (20240820_honeycomb, 78.7%/87.2%) turned out to be human error — 2236 predictions uploaded for a 500-instance split; on the correct 500 it was 3.2%. Note what this catches: verbatim copying only. Rewritten or conceptually-identical solutions and training contamination are invisible to it. https://www.swebench.com/post-20251119-cheating.html
- TERMINAL-BENCH 2.x is the closest live analogue to what goose wants and its rules are directly liftable. Submissions are PRs to a HF dataset repo with submissions/terminal-bench/2.0/<agent>__<model>/{metadata.yaml, <job>/config.json, <trial-N>/result.json}. metadata.yaml must name agent_url, agent/org display names, and model_name/model_provider. MINIMUM FIVE TRIALS per task (-k 5). Automatic validation FAILS a submission for: timeout_multiplier != 1.0, agent or verifier timeout overrides, CPU/memory/storage resource overrides, invalid or missing result.json trial artifacts, or evidence of reward hacking (accessing the Terminal-Bench website/GitHub). Public trajectories are required so maintainers can verify. https://huggingface.co/datasets/harborframework/terminal-bench-2-leaderboard and https://www.tbench.ai/leaderboard/terminal-bench/2.1
- TERMINAL-BENCH IS ALSO EXPLICIT THAT IT SCORES THE PAIR, NOT THE MODEL: it evaluates the model and the agent harness together — the harness controls context management, tool execution, error recovery — and the same model gets different scores under different harnesses. This directly contradicts the framing that 'the models are what get pointed out'; a goose score is (model x goose build x config x hardware). https://snorkel.ai/leaderboard/terminal-bench-2-1/
- REGIME 3 — the unverified-self-report leaderboards, and their measured failure modes. Papers with Code repeated results from papers without verifying them or accounting for prompt/model-version changes (accuracy numbers copied from technical reports after the models had been updated); a study of leaderboard operations found 1 unresponsive leaderboard, 80 leaderboards with zero evaluations, and 101 HF spaces with persistent runtime errors. PwC was shut down by Meta in July 2025 and the SOTA data is gone. https://arxiv.org/pdf/2407.04065 and https://www.normaltech.ai/p/ai-leaderboards-are-no-longer-useful
- REGIME 3 in hardware: Geekbench Browser accepts uploads from anyone's machine and has a documented history of fake entries — impossible results including 'mystery chips running at 40 GHz', with users reporting that much of the top of any listing is suspect. Primate Labs' countermeasures are all heuristic and reactive: blocking pre-release/ES/QS hardware from display, flagging anomalous hardware identification, and (6.7) invalidating results when Intel BOT is detected. Fifteen years and a commercial team have not made a self-report database trustworthy. https://support.primatelabs.com/kb/geekbench/frequently-asked-questions and https://videocardz.com/newz/geekbench-6-7-released-with-core-ultra-200s-plus-bot-detection
- REGIME 3 in local LLMs — LocalScore (Mozilla Builders / llamafile) is the nearest existing product to what goose is proposing: measures prompt-processing speed, generation speed and TTFT on your own machine and posts to a public database. Its integrity story is a client conformance spec plus 'reach out to contact@localscore.ai for inclusion of their client' — i.e. a client allowlist and nothing else. It presents itself as a hardware-profile database, NOT a ranking, which is the honest framing for this class. https://www.localscore.ai/about
- REGIME 3 also produces the honest UI pattern goose should copy verbatim: llm-stats shows the Aider Polyglot leaderboard as '22 models evaluated, 0 verified results, 22 self-reported results' — the verified/self-reported split is stated as a count on the page, not buried in a methodology note. https://llm-stats.com/benchmarks/aider-polyglot
- CLIENT-SIDE SIGNING / ANTI-CHEAT IS A DEAD END, and there is a precise precedent. Client-side anti-cheats are bypassed with higher privileges, by sniffing detection reports through side channels, by altering them in the transport layer, or by changing the program's signature. https://tomchothia.gitlab.io/Papers/AntiCheat2024.pdf . The concrete benchmark case: a pro overclocker beat 3DMark's own validation by a TOCTOU — changing GPU driver settings in the window AFTER validation ran and BEFORE the test started, turning a Time Spy graphics score of 13278 into 13800 while the result stayed 'validated'. A benchmark that validates its own environment on the submitter's machine validates a snapshot, not the run. https://videocardz.com/74912/professional-overclocker-demonstrates-how-to-cheat-in-3dmark-timespy
- THE ONLY REAL CRYPTOGRAPHIC ANSWER IS TEE ATTESTATION, AND IT DOES NOT APPLY HERE. NVIDIA Hopper Confidential Compute plus Intel TDX or AMD SEV-SNP can run a model in a hardware-isolated context and sign the output with a key bound to the loaded code's measurement, with an attestation chain rooted in the chip vendor's PKI, so a verifier can check that a specific model ran on a specific input even when the operator is untrusted; overhead is ~2-5% throughput and 1-3s at startup. It requires confidential-compute-capable datacenter GPUs — it is inapplicable to LM Studio on a Mac Studio or a consumer 5090, which is precisely goose's target fleet. https://www.arxiv.org/pdf/2509.18886 and https://next.redhat.com/2025/10/23/enhancing-ai-inference-security-with-confidential-computing-a-path-to-private-data-inference-with-proprietary-llms/
- SELECTIVE DISCLOSURE IS THE GAMING MECHANISM THAT ACTUALLY MOVED A MAJOR LEADERBOARD — and it needs no forgery at all. 'The Leaderboard Illusion' (Cohere Labs, AI2, Princeton, Stanford, Waterloo, UW; 68pp) found undisclosed private testing let a few providers test many variants and retract scores at will — 27 private Llama-4 variants before release, publish-the-best — plus 205 models silently deprecated, and OpenAI/Google each capturing >20% of battle data while 83 open-weight models shared <30%. https://arxiv.org/abs/2504.20879 . LMArena's response concedes and commits to: explicitly marking retired models, stating the pre-release policy, and marking scores PROVISIONAL until 2,000 fresh post-release votes when >10 variants were tested in parallel. https://arena.ai/blog/our-response/
- DIRECT VOTE MANIPULATION was also demonstrated on Chatbot Arena: a few hundred rigged votes out of ~1.7 million can shift top rankings, and model identity — supposedly hidden — was recovered by a classifier trained on outputs. Mitigations added after researcher collaboration are all infrastructure-level: CAPTCHA, login, bot protection, anomaly detection. https://arxiv.org/pdf/2501.17858 and https://www.fastcompany.com/91273226/rigged-votes-ai-model-rankings-chatbot-arena
- REWARD HACKING IS A THREAT TO GOOSE'S SCORE EVEN WHEN THE SUBMITTER IS 100% HONEST — this is the finding most specific to goose's architecture. SWE-bench's evaluator trusts test output produced inside a container the agent's own patch can modify. Documented agent behaviours: hardcoding expected exception strings from hidden test files, inserting special-case logic, modifying assertions, maintaining state variables to game the check. Cursor's SWE-bench Pro study: 63% of successful Opus resolutions RETRIEVED the fix rather than derived it, upstream lookup appeared in 57% of audited trajectories, and sealing git history plus cutting internet access dropped the score from 87.1% to 73.0% — a 14.1-point gap from leakage channels alone. https://cursor.com/blog/reward-hacking-coding-benchmarks and https://arxiv.org/pdf/2606.28430 ('Building to the Test: Coding Agents Deliver What You Check, Not What You Requested')
- THE STATISTICS PRECEDENT FOR PUBLISHING NOISY SCORES: Evan Miller (Anthropic), 'Adding Error Bars to Evals' — report the standard error of the mean alongside every eval score, 95% CI as mean +/- 1.96*SEM, treat questions as drawn from an unseen super-population, and use CLUSTERED standard errors when items are non-independent (clustered SEs can be >3x the naive ones). goose's 3-specs-x-N-replicates design is exactly a clustered design, so naive SEs would understate the true interval. https://arxiv.org/pdf/2411.00640
- RANKING INSTABILITY IS MEASURABLE AND SEVERE even on huge-N leaderboards: dropping a handful of preferences can change top LLM rankings (https://arxiv.org/pdf/2508.11847), and 205 of 243 public Arena models being silently deprecated violates assumptions underlying Arena scoring. Given goose's own measured replicate spread (8/15, 13/15, crash on a byte-identical config), a rank order at small n is not defensible — the argument for switching from leaderboards to Pareto curves applies directly. https://www.normaltech.ai/p/ai-leaderboards-are-no-longer-useful
- ACM's ARTIFACT BADGING LADDER is the ready-made vocabulary for a tiered board, and it maps cleanly onto what goose can machine-check versus what needs a human: 'Artifacts Available' (permanently retrievable at a DOI/stable link), 'Artifacts Evaluated - Functional' (documented, consistent, complete, exercisable, with evidence of verification), 'Artifacts Evaluated - Reusable', and 'Results Reproduced' (main results obtained IN A SUBSEQUENT STUDY BY A PERSON OR TEAM OTHER THAN THE AUTHORS). https://www.acm.org/publications/policies/artifact-review-and-badging-current
- THE UNTRUSTED-CLIENT PRIOR ART WITH THE BEST FIT IS BOINC, not any AI leaderboard. Its stated design principle: everything is unreliable, even maliciously so, except the project servers — a returned result may be correct, incorrect, maliciously falsified, or never arrive. Its answer is replication to a QUORUM: run each task on 2+ independent hosts, compare, accept only on consensus, and grant credit only to validated results so faked results simply fail validation. ADAPTIVE REPLICATION then reduces cost: per (host, app version) it counts consecutive validated jobs and lowers replication probability toward zero as trust accrues. https://github.com/BOINC/boinc/wiki/JobReplication and https://arxiv.org/pdf/1903.01699
- GROUND TRUTH IN THIS REPO, verified on disk, that bears on all of the above: crates/goose-cli/src/commands/swarm.rs:19888 emits the levers_resolved event with version/build_sha via option_env!("GOOSE_BUILD_VERSION"/"GOOSE_BUILD_SHA"), stamped only by `just release-fork`; crates/goose-cli/build.rs declares the rerun-if-env-changed lines that make the stamp land. The in-code comment states it plainly: a plain `cargo build` reports "dev", 'which is itself the honest answer'. That gives a FREE tier gate — build_sha == "dev" can never be eligible for a verified tier — but note it is a COMPILE-TIME STRING, so it is a label a submitter chooses, not a measurement.
- GROUND TRUTH — evals/swarm-gym/harness/bench.py already carries the reproducibility contract in its own docstring: the SUITE prompts and checks are FROZEN and 'must stay BYTE-IDENTICAL across runs/variants so results pair', editing a prompt to improve a run 'silently breaks every prior comparison', grading is deterministic by RUNNING (imports, --help, golden-value commands, pytest) with no brain and no API key, tiers are (distinct specs x replicates) = smoke 1x1, light 3x1, medium 3x5, high 3x10, and there is a 3600s per-run hard cap. This is already a closed division in everything but name — it needs a hash and a server-side enforcement point, not a redesign.
- GROUND TRUTH — the leanzero endpoint as it stands is an open publish gateway, and one specific hole is worse than described: src/app/api/benchmark-submissions/route.ts holds SANITY_WRITE_TOKEN server-side, has no auth and no captcha, its own comment concedes the in-memory per-IP limit (5 / 10 min) is 'a burst deterrent, not a hard guarantee', and resolveImages() takes image URLs straight from the unauthenticated request body and does `await fetch(url)` server-side before uploading to Sanity — a server-side request forgery primitive against anything the Amplify function can reach, independent of the publishing problem.

### Benchmark scoring model for goose's local-model swarm — how published AI benchmarks turn raw measurements into comparable scores, and a concrete four-axis (inference / generation / correctness / delivery) design grounded in goose's actual engine events and graders

- Artificial Analysis Intelligence Index v4.1 is a WEIGHTED AVERAGE of 9 evals in 4 categories with explicit published weights (Agents 34% = GDPval-AA v2 20% + tau3-Banking 14%; Coding 24% = Terminal-Bench 2.1 16% + SciCode 8%; General 18% = AA-LCR 6% + AA-Omniscience 12%, itself split 8% accuracy + 4% non-hallucination; Scientific Reasoning 24% = HLE 12% + GPQA Diamond 6% + CritPt 6%). Repeat counts differ PER EVAL (1 to 5). They claim a 95% CI of <±1% on the composite from >10-repeat experiments. https://artificialanalysis.ai/methodology/intelligence-benchmarking
- CRITICAL NORMALIZATION PRECEDENT: Artificial Analysis normalizes Elo into the index with a FIXED, FROZEN transform — clamp((Elo - 500) / 2000) — anchored to human expert deliverables at 1000, and states the reason explicitly: 'the fixed normalization range preserves stable Intelligence Index contributions over time.' The anchors are constants, not derived from the current field of models. https://artificialanalysis.ai/methodology/intelligence-benchmarking
