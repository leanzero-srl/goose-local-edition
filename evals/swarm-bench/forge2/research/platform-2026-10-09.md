# Forge 2.0 research — primary-source notes (2026-10-09)

Scope: what changed in Forge 2026-07-01 → 2026-10-09, current contracts of candidate modules, and the
production-difficulty classes, for designing `forge-2.0`. Builds on `evals/swarm-bench/forge/RESEARCH.md`
(2026-10-02) and `DESIGN.md` §2.2/§15/§16/§17.2; facts already there are not repeated unless they changed.

## How this was gathered (so it can be re-run)

  `https://dac-changelogs.services.atlassian.com/changes?apiGroups=forge-core-platform,forge-jira-cloud-platform,forge-confluence-cloud,forge-jsw-cloud,forge-jsm-cloud,rovo-mcp,adopting-forge-from-connect&types=Removed,Deprecation%20Notice,Announcement,Added,Fixed,Early%20Access,Request%20for%20Comments%20(RFC)&offset=0&limit=100`
  (`/apiGroups` and `/types` list the filters). 99 Forge-group entries dated ≥ 2026-07-01. Raw JSON and the
  extracted text are in `scratchpad/forge2/raw/forge_*.json`, `raw/forge_changes_since_0701.txt`, `raw/rest_0.json`.
  The `/gateway/api/dac-changelogs` path the page uses returns 401 from curl.
- Doc pages: server-rendered HTML, fetched with `tools/fetchtext.py`; text copies in `scratchpad/forge2/pages/`
  (each file's first line is its URL; "Last updated" dates quoted below come from the page).
- npm: registry JSON + tarballs (`raw/npm_*.json`, `raw/tgz/*/package/CHANGELOG.md`, `@forge/manifest@13.6.0`
  schema, `@forge/api@8.2.0` typings).
- CDAC: Discourse `search.json` and `/t/<id>.json` (`tools/cdac.py <topic> <posts> <chars>`).
- OpenAPI: Jira v3 `https://dac-static.atlassian.com/cloud/jira/platform/swagger-v3.v3.json`, Confluence v2
  `https://dac-static.atlassian.com/cloud/confluence/openapi-v2.v3.json` (both fetched 2026-10-09).

## 2. Candidate modules / APIs — status, contract, trap, emulatability

### 2.1 Forge SQL — GA (no Preview banner; https://developer.atlassian.com/platform/forge/storage-reference/sql/, "Last updated Jun 17, 2026")
- Manifest: `sql` module (schema 13.6.0 has `sql`). "adding Forge SQL to an existing app will require a major version upgrade".
- API (`/sql-api/`): `sql.prepare<T>(q).bindParams(...).execute()` → `{rows, metadata?}`; `sql.executeRaw`; DDL via
  `migrationRunner`; "Dates will be returned as strings"; "Queries that use restricted functions, statements, or
  syntax are rejected with a SQL_POLICY_VIOLATION error" (query policy page `/sql-query-policy/` fetched, not read in full).
- Limits (`/limits-sql/`): 1 GiB prod / 256 MiB staging / 128 MiB dev; 200 tables; "DML Requests per second 150";
  "DDL Requests per minute 25"; "Per-connection timeout for SELECT queries 5 seconds", INSERT/UPDATE/DELETE 10 s,
  DDL 20 s; memory per query 16 MiB; response 4 MiB; "Foreign keys are not supported"; "Each SQL statement can only
  contain a single query".
- Documented traps: "Orchestrate schema migrations through an async event consumer"; "Make every DDL statement
  idempotent"; "each change ... backwards compatible to all schema versions that are currently in use"; "Avoid using
  AUTO_INCREMENT"; use `AUTO_RANDOM` so BIGINT fits the JSON response.
- Emulatable: needs a MySQL-compatible engine. NEW: RFC-148 (CDAC 102858, staff LukeD, 2026-09-24): "we are
  developing a Docker-backed local development experience for Forge Storage"; "@forge/kvs, covering Key-Value Store,
  Custom Entity Store, and Secret Store; @forge/sql, covering Forge SQL. Existing calls through these SDKs are routed to
  local emulators when the local-storage tunnel is enabled"; "Strong API parity (pagination, query behaviour, SQL
  syntax/dialect)"; "Automatically pulls missing public emulator images"; "It is not an EAP, beta, preview, or GA
  feature". Not verified: what the images contain, their licence, whether usable outside `forge tunnel`.

### 2.2 KVS / Custom Entity Store — GA
- KVS transactions (`/storage-reference/kvs-transactions/`, Sep 28): set/delete only; "maximum of 25 operations";
  "Each key can only be used once in a transaction"; "payload size of 4MB"; "treated as a single Write operation ...
  returning a TOO_MANY_REQUESTS error".
- Entity transactions (`/storage-reference/entities-transactions/`, Sep 28): conditional `set`/`delete` with
  `conditions: Filter`, `check(key, ...)` with mandatory conditions; "if any condition is not met, the entire
  transaction will fail". Doc trap: the sample imports `Conditions` but uses `FilterConditions`, and `check`'s sample
  signature (`check('employee5', filter, {...})`) differs from the options form used elsewhere.
- Conditional single writes (`/kvs-api/`): `keyPolicy: 'OVERRIDE' | 'FAIL_IF_EXISTS'`; "If returnValue is provided,
  keyPolicy must be 'OVERRIDE'"; `returnValue: 'PREVIOUS' | 'LATEST'`. Not documented on the page: the exact error
  a `FAIL_IF_EXISTS` collision returns.
- Consistency (`/storage-reference/entities/`): "The entity().query method used by the Custom Entity Store is
  eventually consistent... The entity().get method, on the other hand, is strictly consistent."
- Query (`/entities-api-query/`): "Each query can only target one index"; partition values "in the order they are
  declared"; "returns up to 10 values by default ... maximum of 100"; "the and and or methods are in-memory filters.
  Using them can sometimes produce pages with no results, with cursor pointing to the next page"; "do not persist
  cursors"; type `any` attributes in filters → 422.
- Limits (`/limits-kvs-ce/`, Sep 28): 1000 RPS; 4000 reads and 4000 writes per minute counted in 10 KB units
  ("a request with a payload of 65KB ... count of 7 requests"); key ≤ 500, regex `/^(?!\s+$)[a-zA-Z0-9:._\s-#]+$/`;
  value 240 KiB; depth 31; writes "1 MB/s per key"; 20 entities, 7 indexes, 50 attributes; range attrs ≤ 900 bytes,
  partition ≤ 1700 bytes; "each complex query can only have a maximum of 100 conditions".
- Doc inconsistency: error page (`/kvs-errorhandling/`, Mar 2024) says "maximum object depth (32)", limits page says 31.
- Backport limit (`/versions/`): "Any manifest file changes relating to Custom Entities cannot be backported."
- Emulatable: yes (in-process); the RFC-148 images are the reference to diff against if they become usable.

### 2.3 Async events (`@forge/events` 3.x) — GA (`/runtime-reference/async-events-api/`, Sep 1, 2026)
- Push: `{body, delayInSeconds? (≤ 15 min), concurrency?: {key, limit}}`; "A maximum of 50 events can be pushed per
  request, up to a maximum combined payload of 200 KB"; plain payload throws "Event body must be an object."
- Consumer: manifest `consumer: {key, queue, function}`; handler receives `AsyncEvent {body, jobId, eventId,
  queueName, delayInSeconds?, concurrency?, retryContext?}`; "There is no payload property".
- Concurrency: "Concurrency counters are implicitly scoped to an app installation, but not to a specific queue".
- Delivery CHANGED vs RESEARCH: "guaranteed to be delivered at least once within a defined retention window" of
  "24 hours", extendable "by another 72 hours, to a total of 96 hours" for platform errors; "Async Events are
  automatically retried within the retention window until they are successfully delivered. Retries use exponential
  backoff, with intervals reaching up to approximately 15 minutes"; app-level errors include "runtime error, function
  time out, function out of memory, ... insufficient permissions, reaching invocation limits"; "If the retention
  window is exceeded due to app level errors, the Async Event is dropped." `retryContext.retentionWindow
  {startTime, remainingTimeMs}`; "Platform-level errors do not increment" `retryCount`.
- `InvocationError({retryAfter (≤ 900, higher lowered), retryReason: FUNCTION_RETRY_REQUEST |
  FUNCTION_UPSTREAM_RATE_LIMITED, retryData ≤ 4KB})`.
- Jobs: `queue.getJob(jobId).getStats()` → `{success, inProgress, failed}`; `cancel()`.
- Limits (`/limits-async-events/`, Feb 26): 500 events/min; 100 KB per event when timeout > 55 s; "Cyclic invocation
  limit 1000 ... push requests ... across all handlers originating from a single initial function invocation".
- Contrast with PRODUCT events (`/events-reference/product_events/`, Aug 6): "You can only retry an event for a
  maximum of four times"; "Because of the bug (ECO-734), retryData should be of an object type, otherwise it is not
  sent on retry." Install events: "Forge will retry up to 4 times" (lifecycle page sample comment).
- Ordering: not FIFO — staff, CDAC 74415/2 (§3).
- Emulatable: yes; the emulator owns delivery so it can inject redelivery, reordering and retention expiry.

### 2.4 Invocation timeouts and rate limits — GA (`/limits-invocation/`, Sep 1, 2026)
- 25 s runtime for user/webtrigger/scheduled "Additional invocation limits" table row 1; "5" s for "events invoked by
  Forge Remote"; 900 s for "function modules that are only referenced by consumer or scheduled trigger modules.
  Default timeout is 55 seconds"; 55 s for "web trigger, action and rovo:agentConnector modules"; "Single outbound
  request timeout (async events) 180".
- Egress "100 per runtime minute (rounded up)" per invocation; "Network requests 3,000,000 requests per minute, per
  app and 100,000 requests per minute, per app, per tenant"; memory default 512 MB up to 1,024 MB.
- Front-end 429 handling: `invoke(key, payload, {rateLimitProperties: true})`, `error.metadata?.rateLimitProperties?.rateLimitReset`;
  webtriggers: retry after `X-Ratelimit-Reset`.
- Scheduled trigger (`/manifest-reference/modules/scheduled-trigger/`, Jun 17): intervals "fiveMinute, hour, day, or
  week"; "about 5 minutes after app deployment"; "If the function throws an error, nothing will happen, and the
  function invocation will not be retried"; installs spread "evenly across the interval"; "There is a small chance of
  duplicated invocations"; `filter: {appIsLicensed}`.
- Trigger (`/manifest-reference/modules/trigger/`, Jul 29): new `payload.include.propertyPaths` ("entity property paths
  whose values are resolved and included in the delivered event payload"); `filter.onError` (`RECEIVE_AND_LOG`,
  `RECEIVE`); "Events for trigger modules may take up to 3 minutes".

### 2.5 Web trigger — GA module; HMAC auth present in schema/SDK/CLI but NOT on the module doc page
- Module page (`/manifest-reference/modules/web-trigger/`, Apr 17): `urlFormat: v1|v2`; `response.type:
  static|dynamic`, static `outputs[{key, statusCode, contentType?, body?}]`, function returns `{outputKey}`; "only static
  web triggers are eligible for the Runs on Atlassian program"; "Adding a new dynamic web trigger" = major version;
  "By default, the URLs ... have no built-in authentication"; "asUser API calls will not work in web trigger functions".
- Request (`/events-reference/web-trigger/`, Nov 2024): `{body: string, headers: {name: string[]}, method, path,
  userPath, queryParameters: {k: string[]}}`; incompatible result → 500.
- HMAC: `@forge/manifest` 13.6.0 schema: `webtrigger[].request.authentication` enum `["hmacSharedSecret", "none"]`;
  CLI `forge webtrigger create --readSecretKey` "read the secret key for an authenticated (HMAC) web trigger from
  stdin", `--noKeyExpiry`; `@forge/api` 8.1.0 `secretKeyConfig`. NOT FOUND in any doc page I read: the signature
  header name, the HMAC algorithm/canonical string, or whether the platform verifies before invoking. Not emulatable
  faithfully until a page documents it.

### 2.6 apiRoute (Forge app REST APIs) — Preview (`/manifest-reference/modules/api-route/`; `/app-rest-apis/`, Jun 8)
- Manifest: `apiRoute: {key, path, operation (GET|POST|PUT|DELETE|PATCH), function, accept: [application/json],
  scopes: [...:custom]}`; developer scopes in `custom-scopes.yaml`; "limit of 20 developer-defined scopes per app per
  environment"; schema path pattern `^/[a-zA-Z0-9]+(/[a-zA-Z0-9]+|/\*)*/\*\*$|^/[a-zA-Z0-9]+(/[a-zA-Z0-9]+|/\*)*$` (no
  `{id}` placeholders — yet the overview cites "/employees/{id}"); the property table calls the method `method` but the
  YAML and schema use `operation`.
- Security: "For each site, app REST APIs are disabled by default"; 3LO only; "Only members of the site ... can
  create the 3LO integration".
- Handler: tutorial returns `{statusCode, body, ...}` ("you need to specify the statusCode"); the REQUEST object's
  shape is not documented (sample just `JSON.stringify(req)`). URLs: `https://api.atlassian.com/svc/<product>/<cloud-id>/apps/<app-id>_<env-id>/<path>`.
- Emulatable: routing + scope check + admin toggle yes; request shape would be invented → low fidelity.

### 2.7 App-managed permissions / Rolling releases — Preview (`/rolling-releases/`, Aug 27; CHANGE-3315)
- Manifest: `permissions.enforcement: app-managed`. "Rolling releases decouple permissions (scopes and egress) from
  app code versions"; "if the app attempts an action that requires a permission not yet granted, it will encounter a
  permission denied error or have its external request blocked"; "Atlassian will not roll back your app if issues arise".
- SDK: backend `permissions.hasScope(s)`, `permissions.canFetchFrom('backend', url)`, `permissions.canLoadResource`,
  `permissions.hasPermission({scopes, external}) → {granted, missing}` ("You must extract the granted property");
  Custom UI `checkPermissions({...}).then(({granted, missing}) => ...)`; UI Kit `usePermissions`.
- Trigger filter: `event.permissions.scopes.includes('write:jira-work')`; upgrade event payload carries `permissions`;
  "The upgrade event is not triggered for code-only upgrades".
- Testing: `forge install --upgrade code --major-version 4` installs a decoupled state.
- No "app roles" module page exists (404 at `/app-roles/`); I found no app-roles feature in the changelog window.
- Emulatable: yes and cheap — run the same build under two permission sets and grade graceful degradation.

### 2.10 `jira:customField` / `jira:customFieldType` — GA (Jul 8)
- Value function: "invoked on every issue view"; input `{field: {id, key, type, name}, issues: [{id, value}]}`;
  "The order of values returned must be the same as the order of issues received"; "asUser isn't supported"; "make
  sure your function has constant performance regardless of the number of issues".
- Read-only fields: set via `PUT /rest/api/3/app/field/{fieldIdOrKey}/value` / `POST /rest/api/3/app/field/value`;
  "Validation takes place whenever an issue is edited or created, but not when the app updates the value directly".
- Rendering: "Forge apps can provide rendering of the field with UI Kit. Custom rendering currently can't be
  implemented using Custom UI or Frame component." Collections up to 100 values (string/group/user only).
- Lifecycle: data reappears if reinstalled within 30 days; "changing the data type after the field has been used ...
  undefined behavior". `searchSuggestions` expression/function; search aliases.
- Emulatable: the value function, validation expression and private update API yes; view rendering needs UI Kit (no).

### 2.11 Workflow rules — Preview (validator Mar 12 2025; condition, post function Jan 13 2026)
- Validator: Jira expression (`expression`, `errorMessage`; "If the expression returns a string value, that value will
  be shown as the error message") OR function: input `{issue: {key}, configuration, transition: {from: {id}, to: {id}},
  modifiedFields}`; return `{result: boolean, errorMessage?}`; `modifiedFields` "only if read:jira-work"; config via
  `workflowRules.onConfigure(() => JSON.stringify(cfg))`, read at `extension.validatorConfig`; new-editor config

### 2.12 `jira:jqlFunction` — GA (module page Mar 9; architecture page `/cloud/jira/platform/jql-functions/`, Oct 9) — contract now captured (§16 said it was not)
- Manifest: `{key, name, operators [!=, >=, <=, in, not in, ~=, is, is not], types [...], arguments [{name, required}], function | endpoint}`.
- Input: `{precomputationId, clause: {field (canonical, e.g. "key" not "issue"), type: [...], operator, functionName, arguments: [...]}}`.
  Output: `{jql: "id in (1, 2, 3)"}` or `{error, storeErrorAsPrecomputation?}`.
- Semantics: "Jira evaluates each custom function once and saves the result" (precomputation); "Precomputations are not
  scoped to users"; "Precomputations not evaluated for 7 days are removed automatically"; "limit of 1,000 right-hand
  side values in the JQL fragment"; "Forge-provided functions have a time limit of 25 seconds"; timeout error "may be
  cached for up to 1 minute". App must keep precomputations fresh: `GET /rest/api/3/jql/function/computation`,
  `POST .../computation` (update), `POST .../computation/search`.
- CHANGE-3506: invalid custom-function JQL now 400s directly on `/search/jql`.
- Emulatable: yes, strongly — the mock search engine substitutes fragments, caches them, and grades staleness after
  an issue event; the 1,000 cap and user-agnostic caching are crisp checks.
