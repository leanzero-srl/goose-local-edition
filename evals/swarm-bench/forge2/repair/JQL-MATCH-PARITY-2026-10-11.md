# Native JQL match API parity

The current [Jira Cloud issue-search API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/#api-rest-api-3-jql-match-post) and shipped `openapi/jira.json` expose `POST /rest/api/3/jql/match`. The existing Forge2 site charged it as a read-like POST but had no handler, so a model taking this legitimate batching path received `501 EMULATOR_NOT_MODELLED`. This was a framework gap, not evidence that the model's permission implementation was wrong.

The modeled body is `{issueIds: [integer IDs], jqls: [JQL strings]}`. At most 50 unique IDs and 10 queries are permitted; the two limits and their verbatim OpenAPI receipts now live in `site/limits.cjs`. The pinned schema has no minimum array size. A successful response returns `{matches: [{matchedIssues: [numeric IDs], errors: []}, ...]}` in input-query order. Invalid JQL produces an error in its own result row at HTTP 200; a malformed body returns HTTP 400. The explicit issue-ID list bounds evaluation, so native search's unbounded-query refusal does not apply. Numeric IDs work with both `issue in (...)` and `id in (...)` aliases.

Each row resolves only the requested IDs from current site state and applies the actual querying identity's Browse and issue security permission before evaluating its JQL. There is no saved permission result. A revoked person loses the issue immediately; deleted and nonexistent IDs are omitted. Registered custom functions expand through exactly the same installed in-process or private remote callback host and caller-independent native precomputation cache as ordinary search. The final matches are still filtered for the person on every call. Evidence is recorded as `jqlExpansions` on the actual request entry. Valid Jira syntax outside the site's modeled subset retains the existing loud 501/harness-missing behavior.

The existing disclosed tariff interprets this response as one result envelope: 1 base + 1 core record = 2 quota points for a charged app request. It is a read-like POST, so no per-issue write window is consumed. This count is a benchmark interpretation of Jira's cost classes, not a claimed Atlassian per-endpoint price. The implementation does not raise the quota or change rate semantics.

Trace: a golden person-facing membership check with 50 issue IDs previously entered the pinned route and scopes, then the missing-handler branch and returned 501. With the native handler, it evaluates that exact list and returns only visible IDs, allowing the golden's independent, uncached access check to use one request per 50 IDs. Would have changed the outcome: YES, the former harness refusal becomes the legitimate JQL-match path; a hidden or revoked issue remains absent. This fixes host parity, not the candidate's scoring predicate.

Verification: seven focused tests pass against actual HTTP requests and the real `@forge/api` asUser resolver, including both scoring and remote dev native-function hosts. They cover query order, issue/id aliases, unrestricted predicates, numeric output IDs, 50/10 boundaries, malformed types, per-JQL errors, classic/granular scopes, explicit harness gaps, same-ID security positive controls, Browse revocation, deletion while the same person remains authorized, and shared native cache with fresh user permission checks. Twenty-three existing native JQL host, site/OpenAPI and precomputation tests pass after sharing expansion plumbing. No model calls or full scorer run were needed.

The public starter can state that `POST /rest/api/3/jql/match` is supported, accepts up to 50 numeric issue IDs and 10 JQL strings, and applies the requesting person's current Browse and issue security permissions. The shipped OpenAPI gives models its full request and response reference. The parent owns public-contract wording and the golden consumer.
