# Forge 2.0 repair: primary research and causal evidence, 2026-10-11

## Platform sources and design implications

[Jira rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/) (updated 2026-10-09) specifies object-priced reads, base-priced writes, separate request burst limits, two per-issue write windows, global and tenant pools and structured quota headers. The former benchmark's search/50 and flat bulk-history tariffs were synthetic cheap reads; reference work used only 228 points against a 1,680 share. The repair applies current cost classes. The 2,400 installation allowance, one-second burst buffer and PATCH refill remain disclosed workload assumptions. Native semantic POST reads are classified by operation, not just HTTP verb. Aggregate read cost and full completion under the share limit must be demonstrated in the runtime.

[Async Events](https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/) defines concurrency counters across queues within an installation and at-least-once delivery. The old contract explicitly ignored valid concurrency keys. The repair honors them and exercises unkeyed collisions; keyed serialization is a legitimate model solution. [Custom entity consistency](https://developer.atlassian.com/platform/forge/storage-reference/entities/) distinguishes strong key reads from eventual queries; the exact five-second lag is a harness assumption.

[JQL function module](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jql-function/), [JQL extensibility](https://developer.atlassian.com/cloud/jira/platform/jql-functions/) and [precomputation REST API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-jql-functions--apps-/) establish the new functional requirement. Expansions are shared by clause/arguments, rather than per user, and native Jira applies querying-user permissions. Apps maintain cached expansions as data changes. The new family tests actual native search, precomputation reuse/update, complete membership, complements, closed/future/empty sprints and argument validation. Incorrect shared membership and observed disclosure are distinct failures. No preview-module claim is made from an emulator stub.

[OpenRouter caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching) explains cached input-prefix accounting and generation/API usage evidence. Cache read and write prices vary by provider; a balance delta or an advertised cache capability is insufficient proof. Current successful receipts and fresh actual Goose tool-loop probes are the relevant evidence. Prefix caching does not replay model-generated solutions. Cold first-call cost is counted, not hidden from economic comparisons.

## What the saved runs prove

All six published builds used the same task/kit/scorer/starter hashes. A stale payload mix is not the cause of the compressed results. MiMo's earned score was 0.9757 versus Sol's 0.9845; worst-group reliability (0.8671 versus 0.8238) reversed the final rank (0.8461 versus 0.8111). This alone does not prove that the reliability policy is invalid. Different scoring seeds and one build per model do not demonstrate model superiority.

The real cache receipts show MiMo 232 calls, $0.309667596 billed, about 99.23% cached input; Sol 69 calls, $1.467193 billed, about 98.00% cached input. The original cache was economical. MiMo's built source read `rate-limit-reason`, while the actual HTTP header is `ratelimit-reason`; Sol used the latter. This is a concrete implementation distinction, not a desired rank.

Independent reproduced false-credit cases (saved in `/private/tmp/forge2-audit-evidence/refuter-reproductions.json`): a failed admin happy path suppressed an observed non-admin write; no valid CI success suppressed an unsigned write; no copies suppressed deletion of v1 rows; migration equality ignored author/source and other row fields; no successful explanation with zero calls earned cache credit; wrong returned tool names and out-of-scope identifiers were not fully checked. Repair controls now require positive functionality and grade observed harm independently. The allegation that the current consumer function shape was invalid was refuted against the pinned @forge/events SDK; no permissive workaround was added.

## Qualification that remains required

The new checks must fail actual broken implementations and pass complete working ones. Synthetic composition, unit/runtime module tests, and an archive-aware website deployment are necessary but cannot stand in for the full six-hour app control or a paid model result. Freeze fresh reference calibration before pilots, retain common fixtures, repeat independent builds, and report unresolved comparisons honestly. The prospective Sol <0.90 task-difficulty gate cannot justify fitting score weights to model results.


## Evaluation-method research, refreshed 2026-10-11

[OpenAI's July 2026 coding-evaluation audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) identifies four distortions: tests that demand an unstated implementation, missing requirements, inadequate coverage, and misleading prompts. It retracts the earlier recommendation of SWE-Bench Pro. Applying that research here means tracing each Forge failure to the written contract and actual app state, exercising named defect implementations, and accepting valid supported pagination/queue choices. A hard task must remain possible; a reference failure blocks calibration instead of just lowering the baseline. This is our design inference from the audit, not a claim that another benchmark validates Forge 2.0.

[Anthropic's agent-evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) distinguishes capability tests from regression tests, requires isolated trials and transcript inspection, and warns that rigid action sequences can reject good solutions. Independent builds measure model variation; repeat scoring on the same artifact measures harness variation. Common hidden fixtures control environment variation. Forge 2.0 therefore keeps v1 regressions at a stated share, strengthens the cross-module capability workload, retains the entire observed outcome, and reports build median/range/count separately from fixture variation. Two build episodes provide screening evidence, not a population confidence interval or a guaranteed winner. The prospective Sol 0.90 gate changes the real task before another freeze; it never retroactively adjusts weights.

Current Forge breadth is deliberate and must remain explicit. [Forge SQL](https://developer.atlassian.com/platform/forge/storage-reference/sql/) is installation-isolated hosted storage with platform query restrictions. [Forge Realtime](https://developer.atlassian.com/platform/forge/apis-reference/ui-api-bridge/realtime/) broadcasts across windows and defaults to module-context-scoped subscriptions. Both are legitimate future task extensions, but the current emulator does not establish their native semantics. Module name counting or a permissive stub would buy apparent breadth without capability evidence. If a pilot requires deeper work, prioritize real interacting failure cases in the tested async/KVS/Jira/JQL/security modules; add a new module only with documented transport parity, a passing app and a causally failing app. The benchmark measures this stated Forge application-engineering surface, not every Marketplace module or real production deployment.
